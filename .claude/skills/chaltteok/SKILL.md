# 찰떡 — 개떡 요청 → 상세 프롬프트 → 실행

사용자가 던지는 한 줄짜리 막연한 지시("UI/UX 검토해줘")를, 추측으로 바로 실행하지 않는다. 먼저 **의도를 적극 추론해 상세 프롬프트로 부풀리고**, 그 해석이 맞는지 **딱 한 번 확인받은 뒤** 실행한다. 이렇게 하는 이유: 막연한 지시를 추측으로 곧장 실행하면 범위·산출물이 빗나갔을 때 비싼 작업(특히 Workflow fan-out)을 통째로 버리게 된다. 확장 + 1회 확인은 "개떡→찰떡"의 편의를 살리면서 빗나간 실행을 값싸게 막는다.

이 스킬은 **오케스트레이션 프론트엔드**다. 직접 모든 걸 하기보다, 요청을 분류하고 적절한 도구·스킬(`code-review`, `systematic-debugging`, `brainstorming`, `wip-update`, Playwright/Supabase/Sentry MCP, Workflow)로 위임·라우팅한다.

---

## 언제 발동하는가

**명시 호출 전용.** 아래 마커로 사용자가 직접 부를 때만 발동한다. 자동 발동·자동 제안은 하지 않는다 — 마커 없는 지시는 막연하더라도 평소처럼(스킬 없이, 또는 더 구체적인 스킬로) 처리한다. 이렇게 explicit-only 로 둔 이유: 자동 발동은 "이게 막연한 지시인가" 휴리스틱이 brainstorming·git-commit 등과 오발동 경쟁을 일으켜 예측 불가해진다. 호출 비용이 마커 한 단어("찰떡")뿐이라, 자동화로 얻는 편의보다 예측 가능성이 더 가치 있다.

발동 마커:
- "찰떡", "찰떡으로", "찰떡으로 진행", "찰떡 스킬로 해줘"
- "부풀려줘", "알아서 해석해서 해줘", "내 의도 파악해서 진행"

### 발동 후, 곧장 위임이 맞으면 위임한다
마커로 호출됐더라도 Phase 1 분류 결과 **더 구체적인 스킬이 정확히 맞으면** 부풀리기를 최소화하고 그 스킬로 넘긴다 (skill priority: process 먼저):
- 단순 질문·1~2줄 자명한 수정 → 부풀리지 말고 바로 처리.
- git-commit / release-deploy / dev-preview / wip-update / market-api-docs-import 가 정확히 들어맞음 → 그 스킬로 위임.
- "**새 기능을 처음부터 설계·창작**" → `superpowers:brainstorming` 으로 라우팅 (직접 설계 흉내 내지 않음).

## 절차

### Phase 1 — 의도 파악

1. **요청 유형 분류** (아래 라우팅 표). 유형이 프롬프트 템플릿·로드할 컨텍스트·위임 후보를 정한다.
2. **유형에 맞는 ground-truth 만 선별 로드** — 전부 읽지 말고 유형이 가리키는 것만. (이미 컨텍스트에 있는 CLAUDE.md 는 다시 안 읽음.)
3. **5요소 추출**: 목표 / 대상·범위(어떤 파일·화면·도메인) / 산출물 형식 / 성공·검증 기준 / 적용할 CLAUDE.md 룰.
   - 모르는 핵심 요소가 있으면 추측하지 말고 Phase 3 확인 때 함께 묻거나, 합리적 기본값을 명시(assumption 표시)한다. no-speculation 룰 준수.

#### 요청 유형 라우팅 표

| 유형 | 신호 단어 | 로드할 ground-truth | 위임/실행 후보 |
|---|---|---|---|
| 검토·분석 | 검토·분석·감사·리뷰·봐줘·점검 | `design-renewal/`·`ui-system.md`·해당 `features/<domain>/` 코드 | `code-review` 스킬, Playwright MCP(화면), Workflow(다관점·다파일) |
| 수정·구현 | 고쳐·구현·추가·바꿔·붙여 | PRD 해당 §·`architecture/v1/features/`·기존 코드 | `superpowers:test-driven-development`, 인라인 |
| 디버깅 | 안 돼·에러·버그·실패·죽어 | CLAUDE.md "운영 사고 진단 chain"·관련 Edge/어댑터 | `superpowers:systematic-debugging`, Sentry/Supabase MCP |
| 문서·핸드오프 | 정리·문서화·WIP·핸드오프·갱신 | `docs/handoff/`·`architecture/v1/` | `wip-update` 스킬, 인라인 |
| 신규 설계 | 만들어·새 기능·설계해·기획 | PRD·`user_flow.md` | **`superpowers:brainstorming` 으로 라우팅** |

### Phase 2 — 상세 프롬프트 작성

추출한 5요소로 구조화된 프롬프트를 만든다. 이게 실행의 기준이 된다:

```
## 목표
<무엇을 달성하는가 — 구체적으로>
## 대상 · 범위
<어떤 파일/화면/도메인. 명시적 경계>
## 수행 단계
1. ...
2. ...
## 산출물 형식
<리포트 구조 / 코드 변경 / 문서 등>
## 성공 · 검증 기준
<무엇으로 완료를 판단하는가>
## 적용 룰 (CLAUDE.md)
<no-speculation, 토큰만, attribution 금지, 2개 산출물 동기화 등 해당하는 것>
## 실행 방식
인라인 | Workflow (에이전트 N개: <각 역할>)
```

### Phase 3 — 확인 게이트 (딱 1회)

전체 프롬프트를 그대로 붙이지 말고 **압축 요약**만 보여준다 (토큰 절감):

```
🔍 이렇게 이해했습니다
- 의도: <한 줄 재진술>
- 목표 / 대상 / 산출물: <각 한 줄>
- 실행 방식: 인라인 | Workflow (N 에이전트)
- (있으면) 가정: <추측한 기본값>

이대로 진행할까요? 수정·추가할 부분 있으면 알려주세요.
```

사용자가 수정 요청 → 반영 후 재확인. 승인 → Phase 4. **이 게이트는 항상 거친다** — 마커로 호출됐어도 승인 전에 Phase 4 로 직행 금지. 이게 빗나간 실행을 막는 안전망이다.

### Phase 4 — 실행

**인라인 vs Workflow 판단 기준:**

- **인라인** (메인 루프에서 직접): 단일 파일/화면, 한 단계로 끝나는 수정, 빠른 분석. fan-out 이득 없음.
- **Workflow fan-out**: 여러 파일·도메인 스윕, 감사/다관점 리뷰, 대규모 마이그레이션, "전수·철저히·모든·구석구석" 류 요청. 독립 병렬 단위가 2개 이상일 때.
  - **이 스킬 호출 자체가 Workflow opt-in 을 성립시킨다** (Workflow 도구 규약: "스킬 지시가 opt-in"). 따라서 광범위 판정 시 사용자에게 따로 "워크플로우 돌려도 되냐" 다시 안 물어도 된다 — Phase 3 승인에 실행 방식이 포함돼 있으므로.
  - 구체적 스킬(`code-review` 등)로 위임이 더 나으면 Workflow 대신 그 스킬을 쓴다.

확정된 상세 프롬프트를 기준으로 실행한다. 중간에 프롬프트 범위를 벗어나는 큰 갈래가 생기면 멈추고 사용자에게 확인.

### Phase 5 — 결과 보고

- 분석·검토류 → 발견 리포트 (우선순위·근거 포함).
- 수정·구현류 → 변경 요약 + 검증 결과 (typecheck/test 통과 여부 — evidence 먼저).
- 어느 경우든 **상세 프롬프트의 성공 기준 대비 무엇이 충족/미충족인지** 명시. 추측으로 "완료"라고 단정하지 않는다.

## 안티패턴 (하지 말 것)

- **추측 실행** — 막연한 지시를 Phase 3 없이 곧장 실행. 빗나가면 fan-out 통째로 낭비.
- **과잉 부풀리기** — 이미 명확한 지시·단순 질문까지 5단계로 늘리기. 자명하면 그냥 한다.
- **전체 ground-truth 통독** — 유형 무관하게 docs 전부 읽기. 유형이 가리키는 것만.
- **확인 게이트에 전체 프롬프트 덤프** — 압축 요약만. 전체 프롬프트가 필요하면 사용자가 "전체 보여줘" 할 때만.
- **신규 기능 설계를 직접 흉내** — 그건 brainstorming 으로 라우팅.
- **확인 없이 실행** — Phase 3 승인 전에 Phase 4 로 직행. 마커로 호출됐어도 게이트는 거친다.
- **마커 없는데 자동 발동** — explicit-only. 마커 없는 막연한 지시는 이 스킬로 끌어오지 말고 평소처럼 처리.
